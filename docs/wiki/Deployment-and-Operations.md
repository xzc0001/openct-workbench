# 部署与运维

## 进程与存储

默认后端绑定 loopback，推荐在前方使用正确配置的 HTTPS 反向代理。
实际来源加入本地 `public_origins`，例如 `https://ct.example.invalid`。
示例域名只用于占位，需替换为自己的实际配置。

账号库在 `auth/`，检查在 `workbench/jobs/`，可再生缓存在 `workbench/cache/`，
集群状态与产物在独立私有目录。账户、密钥、权重不应落在任务清理范围内。
Unix socket 模式需要限制父目录可遍历权限，详见
[部署说明](https://github.com/xzc0001/openct-workbench/blob/main/docs/DEPLOYMENT.md)。

## 计算资源

Windows 使用独立本地进程和线程配置；本公开基础工程不随附原生节点的
Job Object 控制。可选 Linux cgroup v2 将 Web 与计算资源分组。
只有正确配置 systemd 委派后才能设置 `WORKBENCH_RESOURCE_ISOLATION=1`。
Python 外连保护属于纵深措施，系统级网络隔离仍由部署方负责。

不要为了通过单次计算而取消全局隔离、无限放宽内存或静默缩小原始 CT。
资源不足应停止任务并保留输入和上一版结果。

## 升级与清理

1. 记录当前版本，备份账户库和活动检查。
2. 在独立环境验证更新与本地配置兼容性。
3. 维护窗口内升级，检查健康、未登录拒绝、权限与任务恢复。
4. 确认离线旧文件需要重新导出才能获得新版显示功能。

清理先预览范围再确认。仅保留离线预览会移除继续计算所需的部分输入；
删除检查属于数据删除操作，操作前按本地制度备份。

发布仓库更新不代表服务已升级。公开仓库不附带原部署脚本、主机清单或备份。
